# Explorable maps and micro-worlds

Phase B deep pass on one feature idea from the Phase A sweep: an explorable, annotated
representation of a codebase (tree, graph, wiki, diagram) that a person can navigate and put a
directed question to, and Geoffrey Litt's "micro-worlds", throwaway agent-built environments for
inhabiting a system. Documentary only: it records what exists, what is proposed, and what the
sources claim, with no fit assessment and no ranking. Status as observed on 2026-09-13. Each
catalogue entry cites its primary source (tool docs or repository, paper, or the author's own
essay); anything not verified against a primary source is marked as such. The session's web
search budget was exhausted before this pass began, so discovery relied on direct fetches of
known URLs, the GitHub API, OpenAlex and Semantic Scholar metadata, and the Phase A notes; the
[Dead ends](#dead-ends) section lists what that prevented.

## The idea

The Phase A talk note records Litt's third technique, micro-worlds, as agent-built ephemeral
environments after Papert's Mathland, with two demos: a Prolog debugger with a scrubbable timeline
and self-annotations, and a migration "command center"
([talk note, Proposal 3](understanding-bottleneck-talk.md#proposal-3-micro-worlds)); the talk's
lineage runs through Papert's *Mindstorms* and Kay's 1972 Dynabook paper
([talk note, sources](understanding-bottleneck-talk.md#sources-the-talk-draws-on)). The landscape
sweep's Cluster 4 catalogued fifteen map and explain-on-demand tools and asked, for the deep pass,
which of them persist a human's annotations and what became of Mutable Auto Wiki
([sweep, Cluster 4](landscape-sweep.md#cluster-4--explorable-maps-and-explanation-on-demand);
[sweep, observations](landscape-sweep.md#observations-for-the-deep-pass)). The user's own
recollection of "a directory tree you can explore and ask directed questions of, with annotations
appearing" is not in Litt's talk, essay, transcript, or skill
([talk note, dead ends](understanding-bottleneck-talk.md#dead-ends-and-gaps)); this note treats
it as an independent idea and reports the closest things anyone has built. The evidence note
supplies the object these tools are meant to build: a layered mental model whose situation layer
and rationale are the expensive, undocumented parts
([evidence note, program comprehension](evidence-and-mechanisms.md#program-comprehension-what-a-mental-model-of-code-consists-of)).

## Explorable code maps

Entry format: **Name** — map type · how generated · can a person ask a question of a node, and
how · do human annotations persist across regeneration · scope · staleness handling · maturity ·
primary URL.

### Agent-era maps and wikis

- **Windsurf / Devin Codemaps** — hierarchical node map of "the order in which code and files are
  executed and how different components relate", text form with a toggle to "a visually drawn
  Codemap" · generated by "a specialized agent" from a task prompt, a suggested topic based on
  recent navigation, or an agent conversation; "Fast" (SWE-1.5) or "Smart" (Sonnet 4.5) · a node
  click jumps to the file and function; "See more" expands a "trace guide" explanation; a Codemap
  can be `@`-mentioned as context for Cascade or Devin Local, so the question goes to the agent
  with the map attached rather than to the node itself · no annotation or editing feature is
  documented; sharing is by browser link, stored on Cognition's servers on enterprise opt-in ·
  task-scoped; described as "a snapshot of your code" · no regeneration or staleness behaviour
  documented · shipping since 2025-11-04 · <https://docs.devin.ai/desktop/codemaps> and
  <https://cognition.com/blog/codemaps>. The docs draw the contrast themselves: "While DeepWiki
  provides symbol-level documentation, Codemaps help with codebase understanding by mapping how
  everything works together."
- **DeepWiki (Cognition)** — generated wiki: hierarchical pages with Mermaid architecture, flow
  and state diagrams, inline citations to file line ranges, and a "Relevant source files" list per
  page · Devin indexes the repository; effort levels low (free), medium and high (billed in ACUs)
  · "Ask Devin" is repository-level; on a public wiki page (`microsoft/codetour`, observed) there
  is an "Edit Wiki" button, "Last indexed: 20 April 2025", and a "Refresh this wiki" control that
  asks for an email; no per-page ask box was observed · the human's persistent input is
  `.devin/wiki.json`: `repo_notes` (max 10,000 characters each, optional `author`) and a `pages`
  list with `purpose` and optional `page_notes`; when present it replaces automatic planning and
  "only the pages you define in the JSON will be generated, no more, no less" — these are
  instructions to the generator, not annotations on the output · repo-scoped · "We auto-refresh
  DeepWikis if their repo has a badge"; otherwise manual refresh · shipping; MCP server with
  `ask_question`, `read_wiki_structure`, `read_wiki_contents` ·
  <https://docs.devin.ai/work-with-devin/deepwiki>, <https://github.com/CognitionAI/deepwiki>,
  observed page <https://deepwiki.com/microsoft/codetour>.
- **Google Code Wiki** — generated wiki with "architecture, class, and sequence diagrams" plus a
  Gemini chat "that uses the always-up-to-date wiki as context" · "scans the full codebase and
  regenerates the documentation after each change" · chat is repository-level; no node- or
  page-scoped question documented · no human annotation or edit feature documented · repo-scoped
  · staleness is addressed by regeneration ("the docs evolve with the code") · public preview for
  public repositories at codewiki.google (the app page renders nothing without JavaScript); a
  Gemini CLI extension for private repositories is on a waitlist · announced 2025-11-13 ·
  <https://developers.googleblog.com/introducing-code-wiki-accelerating-your-code-understanding/>.
  Secondary reports (not verified) say the CLI extension was still waitlisted in mid-2026.
- **Mutable.ai Auto Wiki** — dead end. `blog.mutable.ai` no longer resolves (DNS failure on
  2026-09-13). The only accounts of what happened are secondary: a PitchBook profile records an
  acquisition by Alphabet on 2024-12-11
  (<https://pitchbook.com/profiles/company/512143-21>) and a Hacker News comment says the company
  "simply disappeared" (<https://news.ycombinator.com/item?id=43740385>). No primary statement was
  found; the Phase A entry stands as the last verified description.
- **Swimm Explore** (missed by Phase A, which listed Swimm only as a living-docs tool) — a
  discovered-module list with, per module, "the details, files, components, and the call tree
  showing where it's used" · "static analysis to automatically understand your repository
  structure, discover modules and their relationships, and then leverages AI to generate
  comprehensive artifacts"; started from an "Analyze Repo" button in the IDE plugin · each module
  offers four directed actions — **Explain** ("module flow, functionality, dependencies, and code
  complexity", with an overview diagram and "extracted business rules"), **Overview**,
  **Diagram** ("a code-coupled dependencies diagram"), **Code** · the generated explanation can be
  edited and saved "as a Swimm doc for your team", which puts it under Swimm's code-coupled
  auto-sync ("This document is automatically kept up to date using Swimm") — the one map in this
  catalogue where the answer to a node question becomes a persistent, human-editable artifact ·
  repo-scoped · staleness of the saved doc handled by Swimm auto-sync; staleness of the module
  analysis not documented · shipping (docs dated 2026) ·
  <https://docs.swimm.io/explore-codebase/> and
  <https://docs.swimm.io/explore-codebase/explain-codebase/>.
- **Understand Anything (Egonex AI)** (missed by Phase A, which had only a secondary mention) —
  interactive knowledge graph in a browser dashboard: "every file, function, and class is a node
  you can click, search, and explore", colour-coded by architectural layer, with a domain view
  ("domains, flows, and steps laid out as a horizontal graph") and a code viewer with "LLM
  annotations inline" · a Claude Code plugin (also installable for Codex, Copilot, Cursor, Gemini
  CLI and a dozen others) whose `/understand` command runs a multi-agent pipeline
  (`project-scanner`, `file-analyzer`, `architecture-analyzer`, `tour-builder`, `graph-reviewer`)
  over a tree-sitter structural extraction; the graph is saved to `.ua/knowledge-graph.json` ·
  the design spec's dashboard has a "CHAT PANEL — Context-aware Q&A about selected nodes /
  project" and "Contextual explanations — click-to-explain"; from the terminal,
  `/understand-explain <path>` deep-dives a file or function and `/understand-chat` answers over
  the graph · no human annotation feature was found (a code search for "annotation" hits only
  extractor and language-lesson code); node summaries are LLM-written and regenerated per file ·
  repo-scoped, or a subdirectory for monorepos · incremental: `meta.json` stores the last analysed
  commit, `git diff <last-hash>..HEAD --name-only` selects files to re-analyse, and
  `--auto-update` installs a post-commit hook; the graph is meant to be committed so "teammates
  skip the pipeline", and a viewer runs from the committed JSON with "no LLM, no API key" ·
  created 2026-03-15, MIT, 82,381 stars and 6,928 forks on 2026-09-13 (GitHub API) ·
  <https://github.com/Egonex-AI/Understand-Anything>; design spec at
  <https://github.com/Egonex-AI/Understand-Anything/blob/main/docs/superpowers/specs/2026-03-14-understand-anything-design.md>.
  Its stated goal: "The goal isn't a graph that wows you with how complex your codebase is — it's
  a graph that quietly teaches you how every piece fits together."
- **GitDiagram** — a system-level Mermaid graph "instead of merely drawing folders" · generated
  by an LLM (OpenAI or OpenRouter) from "a repository tree and README", streamed with an
  explanation · nodes are "interactive source links" to the file or directory on GitHub; no
  question-on-node · no annotations; export is Mermaid source or PNG · repo-scoped · regenerated
  on demand; results persisted per repository · created 2024-12-15, 15,977 stars ·
  <https://github.com/ahmedkhaleel2004/gitdiagram>.
- **CodeBoarding** — "high-level system architecture diagrams" plus "deeper component diagrams
  for important subsystems" and Markdown documentation in `.codeboarding/`, Mermaid output ·
  "static analysis with LLM reasoning" · navigable outputs in IDE, CI and docs; no node question
  documented · docs are Markdown in the repository, so editable, but survival across
  "incremental updates when only part of the codebase changes" is not stated · repo-scoped ·
  incremental regeneration · created 2025-04-08, 2,421 stars; positioned as "See what your AI is
  building before it breaks" and "Keep architecture visible while agents code" ·
  <https://github.com/CodeBoarding/CodeBoarding>.
- **Karpathy's "LLM wiki" pattern** (adjacent; not code-specific) — a Markdown wiki with
  `index.md`, wikilinks and an append-only `log.md`, over immutable raw sources, governed by a
  schema document · the LLM writes and cross-references pages; the human "curates source material,
  directs analysis, asks strategic questions" and keeps editorial control · questions are asked of
  the wiki as a whole · pages persist and compound rather than being regenerated ("the wiki is a
  persistent, compounding artifact"); periodic "lint" passes look for "contradictions, stale
  claims, orphaned pages" · gist dated 2026-04-04 ·
  <https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>. Understand Anything's
  `/understand-knowledge` consumes wikis in this pattern.
- **CodeWiki (research, ACL Findings 2026)** — a framework for "holistic, architecture-aware"
  repository documentation with "architecture diagrams and data-flow representations" across
  seven languages, and CodeWikiBench, "multi-dimensional rubrics and LLM-based assessment
  protocols"; reports a 68.79% quality score against 64.06% for "the closed-source DeepWiki
  baseline" · no human evaluation · <https://doi.org/10.18653/v1/2026.findings-acl.288>.
- **Aider repo map** — ranked text map of files and key symbol definitions, for the model:
  "Aider sends a repo map to the LLM along with each change request"; a graph "where each source
  file is a node and edges connect files which have dependencies" is ranked to fit `--map-tokens`
  (default 1k), "based on the state of the chat" · no human interaction with nodes ·
  <https://aider.chat/docs/repomap.html>.
- **Greptile, Unblocked, Kognita, CodeSee, bloop, Onboard AI** — characterised in Phase A
  ([sweep, Cluster 4](landscape-sweep.md#cluster-4--explorable-maps-and-explanation-on-demand)).
  Verified additions: Greptile "builds a complete graph of your codebase — every function, class,
  and dependency" for PR review; no visual map or persistent Q&A is documented
  (<https://www.greptile.com/docs>). Unblocked answers with links to sources and does not turn
  answers into documentation (<https://docs.getunblocked.com/what-is-unblocked>). `codesee.io`
  now returns 404.

### Code-navigation platforms

- **Sourcegraph code navigation and Cody** — hover, go-to-definition, find-references and
  find-implementations across repositories, "search-based" (text and syntax heuristics) or
  "precise" (compile-time information via SCIP); no visual map in the current docs
  (<https://sourcegraph.com/docs/code-search/code-navigation>). Cody, Enterprise-only, has a
  built-in `explain-code` prompt and an `@` menu for "symbols, directories, files, repositories
  and web URLs" as context (<https://sourcegraph.com/docs/cody/capabilities/commands>,
  <https://sourcegraph.com/docs/cody>). Answers are chat turns; nothing persists to the code
  graph. Sourcegraph Notebooks, the older persistent-explanation feature, is not in the current
  docs (`/docs/notebooks` returns 404).
- **GitHub code navigation and Copilot on repository pages** — jump-to-definition, find
  references and a symbols pane for twenty languages, extracted with tree-sitter for repositories
  under 100,000 files
  (<https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github>).
  The Copilot tutorial "Using GitHub Copilot to explore a codebase" documents directory-, file-,
  symbol- and line-scoped asking from the file view (see
  [Directed questions on a node](#directed-questions-on-a-node)); asking "from the repository
  page" is in public preview. Nothing is stored on the tree: Copilot Chat "stores up to 100 of
  your most recent conversations" for 28 days
  (<https://docs.github.com/en/copilot/how-tos/use-chat/use-chat-in-github>).

### Pre-agent comprehension tools (structure with, in some cases, persistent human notes)

- **Sourcetrail** — interactive graph of symbols and their relationships for C, C++, Java and
  Python; archived by its authors 2021-12-14 ("This project was archived by the original autors
  and maintainers of Sourcetrail by the end of 2021"); 16,488 stars at archive. Bookmarks are the
  annotation feature: a bookmark on any node or edge takes a name, a **Comment** and a category,
  and "Bookmark information is stored within a separate `.srctrlbm` file next to your
  `.srctrlprj` project file", so notes survive re-indexing · repo-scoped · active forks continue
  it: `petermost/Sourcetrail` (pushed 2026-09-11, 757 stars) and Quarkslab's `NumbatUI` (pushed
  2026-06-23) · <https://github.com/CoatiSoftware/Sourcetrail>, documentation at
  <https://github.com/CoatiSoftware/Sourcetrail/blob/master/DOCUMENTATION.md>. The authors' blog
  post on the decision is only on the Wayback Machine, which this environment cannot fetch.
- **SciTools Understand** — dependency, butterfly, data-flow and called-by graphs, "architectures"
  (user-defined logical groupings), and **Annotations**: notes "synchronized with any code entity
  — things like Files, Classes, Namespaces, Functions, even specific lines of code", stored not in
  source but "in the Understand project and each user has their own file", "linked by our parsing
  technology in a way that survives over time and is easily shared via GIT". The vendor's own
  suggested use includes "learn about your code, and leave notes about what your learned" ·
  commercial, active · <https://scitools.com/features> and
  <https://blog.scitools.com/lightweight-but-useful-code-reviews-using-annotations-and-git/>
  (2021-06-17). This is the closest pre-AI instance of a persistent annotation layer over a
  structural map; it has no question-asking.
- **CodeCompass (Ericsson)** — web UI with file manager, "Info tree" of references for a selected
  element, call-path, inheritance and class diagrams, and "CodeBites" (expand a diagram by
  clicking definitions); no annotation feature in the frontend guide · active (pushed 2026-08-05,
  613 stars) · <https://github.com/Ericsson/CodeCompass>.
- **Structure101** — dependency-structure and architecture-diagram tool; acquired by SonarSource
  and no longer sold ("Will Structure101 products still be sold? No"), with capabilities to be
  folded into Sonar products · <https://sonarsource.com/structure101/>.
- **Emerge** — force-directed dependency and filesystem graphs with Louvain clustering and basic
  metrics, generated by a Python scanner into a browser app; goal stated as "getting a better
  understanding of a given software project by using an exploratory approach"; no annotations ·
  1,148 stars, pushed 2026-08-07 · <https://github.com/glato/emerge>.
- **GitHub OCTO repo-visualizer** — a GitHub Action drawing an SVG of the file tree; archived
  experiment · <https://github.com/githubocto/repo-visualizer>.
- **tokei, scc** — line and complexity counters (14,908 and 8,740 stars); they produce tables, not
  explorable maps, and are listed only to close the question ·
  <https://github.com/XAMPPRocky/tokei>, <https://github.com/boyter/scc>.
- **Storey's SHriMP** — the research ancestor: "the embedding of multiple views, both graphical
  and textual within a nested graph display of a program's software architecture"
  (<https://doi.org/10.1109/wpc.2001.921719>); its evaluations are in
  [Evidence](#evidence).

- **Structurizr / C4** — "models as code": the DSL defines one model from which several diagrams

  generating DSL from a photographed workshop sketch or a text prompt ("a little cleanup is

- **Eraser** — "Codebase diagrams" are "AI diagrams generated from a Git repository" from a

- **Multiplayer.app** — the current site is about capturing full-stack session data around issues

## Guided tours and onboarding narratives

- **CodeTour (Microsoft)** — a tour is "a series of interactive steps, each of which are
  associated with a specific directory, or file/line, and include a description". Authoring is by
  recording in VS Code: open files, click the comment bar on a line, write Markdown; steps can be
  **directory steps** (the Explorer focuses the directory and shows a description), selection
  steps, or content steps with no file. The format is JSON in `.tours/` (or `.vscode/tours`,
  `.github/tours`), hand-editable, with `title`, `description`, `ref`, and per-step `file`,
  `line` or `pattern` (a regex "to associate steps with line content as opposed to ordinal"),
  `commands` and `view`. Staleness is handled at authoring time by pinning the tour to a git ref
  (none, branch, commit, tag: "restricted to the current commit, and therefore, will never get out
  of sync") and at CI time by CodeTour Watch / CodeTour Watcher, which "detect tour drift". Steps
  can embed `command:` links, `>>` shell commands and insertable code blocks. What is recorded
  about the reader: only the current step ("Resume Tour"); nothing records which tours or steps a
  person completed, or what they understood. Maintained (pushed 2026-05-05, 4,574 stars) ·
  <https://github.com/microsoft/codetour>.
- **Tour de Code AI** — CodeTour fork that generates "15–25 technical checkpoints" from a Repomix
  dump of the codebase through OpenAI, Anthropic or a local model, ordered "entry → core →
  integrations", with a welcome checkpoint on architecture and purpose; claims "90% faster
  onboarding" with no source · created 2025-11-07, 18 stars ·
  <https://github.com/Tour-de-Code-AI/Tour-de-Code-AI>.
- **"Generating Code Tours Using Locally-Runnable LLMs"** (FSE 2025 companion) — a research plan
  for "debugging-focused code tours" from local models, naming three challenges: "selecting
  relevant code segments", "generating clear and context-aware explanations", and "automatically
  evaluating the quality of generated tours"; goal is "persistent, verifiable documentation
  artifacts" · <https://doi.org/10.1145/3696630.3731462>.
- **Understand Anything guided tours** — the `tour-builder` agent produces "auto-generated
  walkthroughs of the architecture, ordered by dependency", stored under the data directory and
  played in the dashboard's "Learn panel" alongside "language lessons in context of YOUR code";
  `/understand-onboard` writes an onboarding guide · <https://github.com/Egonex-AI/Understand-Anything>.
- **Swimm Playlists** — "a collection of documents, links, videos, Markdown files, and images
  stored as a Playlist collection in a particular order", stored as `.pl.sw.md` files in the
  repository; the one tour format found that records the reader's position: "Swimm keeps track of
  progress in a Playlist, so you don't have to remember where you've left off". Docs inside a
  playlist stay current through Swimm's live snippets and auto-sync ·
  <https://swimm.io/blog/documentation-playlists>, <https://docs.swimm.io/features/>.
- **Swimm /ask and doc generation** — `/ask Swimm` answers coding questions in the codebase's
  context; "Generate doc from PR" and "Generate doc from code snippets" turn a PR or selected
  snippets into a Swimm doc · <https://docs.swimm.io/swimm-ai>.
- **DeepWiki Q&A as narrative** — the wiki's page tree (for `microsoft/codetour`: Overview,
  Architecture, Core Data Model, Tour Player, Tour Recorder, …) is itself a generated reading
  order; questions go to the repository-level "Ask Devin"; nothing records what was read ·
  <https://deepwiki.com/microsoft/codetour>.
- **GitHub's "explore a codebase" tutorial** — a prompt script rather than a tool: overview
  questions ("What are the main entry points and how do the key components fit together?"), then
  "Explain the files in this directory", then "Explain this file", then commits ("What does this
  commit do?") · <https://docs.github.com/en/copilot/tutorials/explore-a-codebase>.
- **Records of what was visited or understood.** Across the tour tools: CodeTour keeps only the
  current step; Swimm Playlists keep per-reader progress; Understand Anything, DeepWiki, Code
  Wiki, Codemaps and Copilot keep nothing about the reader. None records whether anything was
  understood; the nearest is Litt's quiz, which belongs to the explainer, not the map
  ([talk note, Proposal 2](understanding-bottleneck-talk.md#proposal-2-quizzes-as-a-speed-regulator)).

## Micro-worlds

### Litt's two demos

- **Prolog interpreter debugger (December 2024).** Litt was writing a Prolog interpreter "as a
  learning project" and, stuck on unification bugs, "asked Claude Artifacts to whip up a custom UI
  for viewing one of my execution traces." The result: "I could step through an execution and see
  a clear visualization of my interpreter's stack: how it has broken down goals to solve; which
  rule it's currently evaluating; variable assignments active in the current context; when it's
  come across a solution. The timeline shows an overview of the execution, letting me manually
  jump to any point to inspect the state. I could even leave a note annotating that point of the
  trace." Construction: he "copy-pasted my interpreter code and a sample execution trace into
  Claude" with rough requirements and "a fun hacker vibe, like the matrix"; "About a minute later
  (after a single iteration for a UI bug which Claude fixed on its own), I had a solid first
  version". Iteration happened between debugging sessions ("spend a few seconds asking Claude to
  make the change, and then switch back"); "I still haven't looked at the UI code"; one request
  (a flamegraph of the stack over time) failed and was abandoned. Claimed effects: "I caught a
  couple bugs immediately"; "A repeating pattern of solutions in the timeline view led me to
  discover an infinite loop bug"; "I was able to get an intuitive grasp of my interpreter's
  operation". His rule of thumb: "any time I'm spending more than a minute staring at a JSON blob,
  I consider whether it's worth building a custom UI for it." He names the lineage himself: "The
  idea of custom tools for debugging programming systems has been explored in depth by many live
  programming tools; e.g. check out Glamorous Toolkit and Clerk", and frames it as "the dream of
  malleable software: editing software at the speed of thought" ·
  <https://www.geoffreylitt.com/2024/12/22/making-programming-more-fun-with-an-ai-generated-debugger>.
- **Migration command center (2026 talk and essay).** After Claude wrote a site-migration script
  that "was very hard to review: I wasn't familiar with the new framework, and all I could say was
  'I guess that looks about right'", he "asked Claude to make me a video game — a command center
  where I do the port myself, step by step, watching the visible effects and the file tree
  evolve. It produced a UI where I click buttons to run the port step by step, with my old site
  and new site running side by side." Claimed effect: "That left me with a similar understanding
  to doing it by hand — but much faster, because the whole experience was laid out for me." The
  essay's generalisation: "There's a big difference between making a tool for me to debug and
  letting the agent debug — doing it myself is how I develop understanding along the way" and
  "agents can write bits of code that help us humans understand other code" ·
  <https://www.geoffreylitt.com/2026/07/02/understanding-is-the-new-bottleneck>. The transcript's
  "peripheral vision" phrasing and the interactivity caveat ("it can just be a crutch, and it can
  be kind of slop") are quoted in the
  [talk note](understanding-bottleneck-talk.md#proposal-3-micro-worlds).
- **HUD framing (2025).** The debugger reappears as an example of a "head-up display" rather than a
  copilot: "With the debugger, I have a HUD! I have new senses, I can see how my program runs";
  HUDs let you "ambiently build up your own understanding" ·
  <https://www.geoffreylitt.com/2025/07/27/enough-ai-copilots-we-need-ai-huds>.

### The cited lineage

- **Papert, *Mindstorms* (1980).** Mathland: learning mathematics "in 'Mathland'; that is to say,
  in a context which is to learning mathematics what living in France is to learning French."
  Chapter 5 is "Microworlds: Incubators for Knowledge"; the Turtle "defines a self-contained world
  in which certain questions are relevant and others are not", and children "get to know what it
  is like to explore the properties of a chosen microworld undisturbed by extraneous questions."
  Free PDF from the MIT Media Lab: <https://www.media.mit.edu/publications/mindstorms/>.
- **Kay, "A Personal Computer for Children of All Ages" (1972).** The Dynabook scenario: Jimmy and
  Beth modify their Spacewar game to add gravity after Jimmy notices that holding thrust makes the
  ship go "faster and faster, just like Mr. Jacobson said rocks and things do in gravity"; the
  device is "controllable by the child rather than the networks" ·
  <https://mprove.de/visionreality/media/kay72.html>.

### Explorable explanations and live programming

- **Bret Victor, "Explorable Explanations" (2011).** Three kinds — reactive documents, explorable
  examples, contextual information — aimed at "truly active reading": the text becomes "an
  environment to think in" rather than "information to be consumed" ·
  <https://worrydream.com/ExplorableExplanations/>.
- **Victor, "Up and Down the Ladder of Abstraction" (2011).** "the most powerful way to gain
  insight into a system is by moving between levels of abstraction"; control first, abstract
  upward to see all values of a parameter at once, step back down to see why; "The dance is where
  the deepest insights are born—not at any one level of abstraction, but in the transitions
  between them" · <https://worrydream.com/LadderOfAbstraction/>.
- **Victor, "Learnable Programming" (2012).** Five environment demands — read the vocabulary,
  follow the flow, see the state, create by reacting, create by abstracting — with "The entire
  purpose of code is to manipulate data, and we never see the data" and "live coding, on its own,
  is not especially useful"; explicit lineage to Logo, Smalltalk and HyperCard ·
  <https://worrydream.com/LearnableProgramming/>.
- **Nicky Case, Explorable Explanations hub.** "a hub for learning through play" by "a
  disorganized 'movement' of artists, coders & educators who want to reunite play and learning";
  listed on Case's own site among their work · <https://explorabl.es/>, <https://ncase.me/>.
- **Glamorous Toolkit and moldable development (feenk).** The environment's 2026 homepage opens
  with the claim at issue in this whole research programme: "Code reading is the bottleneck.
  Systems are too large, and AI generates code too fast. Glamorous Toolkit replaces reading with
  deterministic contextual tools that compress the system around each problem, helping humans and
  AI explore faster." Thesis: "Software is shapeless. You cannot perceive anything in a software
  system except through a tool"; "Standard tools are useful for generic problems. Contextual tools
  are for all the specific questions that emerge inside a concrete system"; the shipped image
  carries "more than 6000 contextual tools that we relied upon when developing the environment
  itself"; "tools should come to where you are, instead of you invoking them explicitly"; a view
  on an object "offers a unit of documentation" from which "defined narratives" are built for
  humans and for AI; and, under "Do I need this environment in the AI age?", "More than ever."
  Moldable development is defined as "a way of programming through contextual micro tools built
  for each problem", optimising "the single largest expense in software development: figuring the
  system out" · <https://gtoolkit.com/>, <https://moldabledevelopment.com/>. The page gives no
  empirical evidence.
- **Clerk (Nextjournal).** "Moldable Live Programming for Clojure": namespaces become notebooks
  that "always evaluate from top to bottom" inside the running process; alpha ·
  <https://github.com/nextjournal/clerk>.
- **Pharo inspectors.** "Every object in the system can be examined and changed"; the inspector
  can "visualize your objects in many ways (textual form, graphical representation)"; the debugger
  can "save complete state of your program during debugging and restore it" ·
  <https://pharo.org/features>.
- **Observable, Val Town, Replit.** Observable's documentation returned HTTP 429 on every attempt
  and is not characterised here (<https://observablehq.com/>). Val Town describes itself as a place
  where "you—and your AI agent—write and run JavaScript, always deployed in 100ms", with a built-in
  assistant, Townie; its docs say nothing about throwaway tools (<https://docs.val.town/>). Replit
  was not fetched.

### Agents generating bespoke UIs, 2024–2026

- **Claude Artifacts (2024-06-20).** Generated "code snippets, text documents, or website designs"
  in a side window the user can "see, edit, and build upon … in real-time"; the substrate Litt's
  debugger was built on · <https://www.anthropic.com/news/claude-3-5-sonnet>. Anthropic's later
  "Imagine with Claude" page could not be fetched (404 at two URLs).
- **Google Research, "Generative UI" (2025-11-18).** Models generate "immersive experiences and
  interactive tools and simulations, all generated completely on the fly for any prompt" as
  HTML/CSS/JS; evaluation is rater preference — generative UI "strongly preferred by human raters
  compared to standard LLM outputs", second to expert-designed sites; limitations "a minute or
  more" to generate and occasional inaccuracy. Examples are a fractal explorer and a maths game,
  not developer tools ·
  <https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/>.
- **Litt, "Malleable software in the age of LLMs" (2023-03-25).** Predicts "One-off GUIs: People
  use AI to create entire GUI applications just for performing a single specific task—containing
  just the features they need, no bloat", citing Sean Grove's estimate of "50% long-tail,
  on-the-fly UIs generated for specific tasks, used once, then vanish"; argues that within a
  computational medium "the user's reliance on the AI gently decreases over time" ·
  <https://www.geoffreylitt.com/2023/03/25/llm-end-user-programming>.
- **Ink & Switch, "Malleable Software" (June 2025; Litt, Horowitz, van Hardenberg, Matthews).**
  Reports AI-built tools inside their Patchwork environment "in just a few minutes—in the middle of
  a writing session"; "AI is a useful complement to a malleable environment" ·
  <https://www.inkandswitch.com/essay/malleable-software/>.
- **Glamorous Toolkit's AI integration (2026).** "Explainable agent actions: Don't take for
  granted what the AI says it does. Understand it deterministically through contextual views";
  live objects can be passed into a conversation and structured objects returned "each with
  contextual views that make them explorable for both humans and AI" · <https://gtoolkit.com/>.
- **Research.** OpenAlex searches for LLM-generated debugging or visualisation UIs evaluated with
  developers returned nothing on point; the nearest is "Beyond Code Generation: LLM-supported
  Exploration of the Program Design Space" (CHI 2025), an IDE that shows alternative problem
  framings and tracks design decisions (<https://doi.org/10.1145/3706598.3714154>). No study of a
  micro-world in Litt's sense was found.

## Directed questions on a node

Tools where the unit of question is a file, directory, symbol, module or diagram node rather than
a free chat box, and whether the answer is stored.

- **GitHub Copilot on github.com** — four scopes documented in the tutorial: a **directory**
  ("Navigate to the directory … click the Copilot icon … Copilot will use the directory contents
  as context … Ask Copilot: `Explain the files in this directory`"), a **file** (`Explain this
  file`, or for large files a structured prompt), **selected lines** (select by line number, click
  the Copilot icon beside the selection, or "click the downward-pointing button … then choose one
  of the options" for a predefined question), and a **symbol** (highlight it with the file shown in
  split screen). Storage: chat history only, 100 conversations, 28 days ·
  <https://docs.github.com/en/copilot/tutorials/explore-a-codebase>.
- **Cursor `@` mentions** — `@auth.ts` or `@src/components/` attach files or folders ("type /
  after selecting a folder to navigate deeper"); also `@Terminals`, `@Chats`, `@Commit`, `@Branch`,
  `@Browser`; the docs' own advice is "Use @ mentions when you know which files are relevant. If
  you're not sure which files matter, skip it — Agent finds relevant files through its own
  search." Answers are chat turns · <https://cursor.com/docs/context/@-symbols>.
- **JetBrains AI Assistant "Explain Code"** — select a fragment, right-click or Alt+Enter, "AI
  Actions … Explain Code"; "The AI Chat tool window will open to provide you with an explanation";
  injected fragments (regex, SQL, cron) are detected; no save documented ·
  <https://www.jetbrains.com/help/ai-assistant/explain-code-with-ai.html>.
- **Sourcegraph Cody** — built-in `explain-code` prompt; `@` menu for "symbols, directories, files,
  repositories and web URLs"; Enterprise only; answers not persisted to the graph ·
  <https://sourcegraph.com/docs/cody/capabilities/commands>.
- **Swimm Explore** — the question is chosen from a fixed menu on a discovered module (Explain,
  Overview, Diagram) and the answer can be saved as a code-coupled Swimm doc; the only entry here
  where a node answer becomes a persistent annotation ·
  <https://docs.swimm.io/explore-codebase/explain-codebase/>.
- **Understand Anything** — "Context-aware Q&A about selected nodes / project" in the dashboard
  chat panel; `/understand-explain src/auth/login.ts` from the terminal; LLM node summaries are
  stored in the graph JSON and regenerated per changed file; human notes are not a feature ·
  <https://github.com/Egonex-AI/Understand-Anything>.
- **Codemaps** — a node is a navigation target and a "trace guide" holder; a question is posed by
  `@`-mentioning the whole Codemap in the agent input · <https://docs.devin.ai/desktop/codemaps>.
- **DeepWiki** — repository-level Ask; page-level asking was not observed; `page_notes` in
  `wiki.json` let a human steer a page's generation · <https://docs.devin.ai/work-with-devin/deepwiki>.
- **Nam et al., "Using an LLM to Help With Code Understanding" (ICSE 2024)** — an IDE plugin with
  "four high-level requests without the user having to write explicit prompts: to explain a
  highlighted section of code, provide details of API calls used in the code, explain key
  domain-specific terms, and provide usage examples for an API", plus open-ended prompts
  contextualised to the program; the research instance of a directed question on a selection ·
  <https://doi.org/10.1145/3597503.3639187>.
- **Pre-AI persistent annotations on a node** — Sourcetrail bookmarks with comments (`.srctrlbm`),
  Understand Annotations (per-user files in the project, Git-shareable, parser-linked to entities
  and lines), and CodeTour steps (a Markdown description pinned to a directory, file or line and
  checked in). None of these answers a question; each stores what a human wrote.

No tool was found that combines all three of the user's elements — a navigable tree or graph, a
question directed at a node, and the answer persisting as an annotation on that node across
regeneration. Swimm Explore comes closest (menu question, saved doc); Understand stores human notes
without asking; Understand Anything and Copilot ask without storing.

## Evidence

What program-comprehension studies of visualisation and navigation aids show, and what they do
not.

- **Storey, Wong and Müller (WCRE 1997; *Science of Computer Programming* 2000).** "a user study
  that compares three tools for browsing program source code and exploring software structures.
  In this study, 30 participants used these tools to solve several high level program
  understanding tasks"; the conclusion is a design principle rather than a winner: "Program
  understanding tools should enhance or ease the programmer's preferred strategies, rather than
  impose a fixed strategy that may not always be suitable" ·
  <https://doi.org/10.1109/wcre.1997.624572>, <https://doi.org/10.1016/s0167-6423(99)00036-2>.
  Storey's 2005/2006 review, already in Phase A, adds that tools mostly support the program model
  and rarely the situation or domain model
  ([evidence note](evidence-and-mechanisms.md#program-comprehension-what-a-mental-model-of-code-consists-of)).
- **Ko, Myers, Coblenz and Aung (*IEEE TSE* 2006).** Developers given an unfamiliar program for
  70 minutes "interleaved three activities" — search, relate by following dependencies, collect —
  "based their searches on limited and misrepresentative cues", "lost track of relevant code" held
  only in tabs and scroll positions, and "spend, on average, 35 percent of their time performing
  the mechanics of navigation within and between source files"; the paper proposes "a new model of
  program understanding grounded in theories of information foraging" ·
  <https://doi.org/10.1109/tse.2006.116>.
- **Lawrance et al. (*IEEE TSE* 2010/2013).** Ten professional programmers debugging a real
  open-source program: "the programmers' verbalizations far more often concerned scent-following
  than hypotheses", and an executable foraging model "predicted programmer navigation behavior
  more accurately than comparable models that did not consider information scent" ·
  <https://doi.org/10.1109/tse.2010.111>. Piorkowski et al. (CHI 2013): nine professionals "spent
  50% of their time foraging" · <https://doi.org/10.1145/2470654.2466418>.
- **Sillito, Murphy and De Volder (FSE 2006; *IEEE TSE* 2008).** Two qualitative studies
  (newcomers on assigned tasks; industrial programmers on their own tasks) yield "a catalog of 44
  types of questions programmers ask during software evolution tasks" and "a description of how
  existing deployed and proposed tools do, and do not, support answering programmers' questions" ·
  <https://doi.org/10.1145/1181775.1181779>, <https://doi.org/10.1109/tse.2008.26>.
- **LaToza and Myers (PLATEAU 2010).** 179 professional developers reported 371 hard-to-answer
  questions, clustered into 21 categories and 94 distinct questions; "The most frequently reported
  categories dealt with intent and rationale — what does this code do, what is it intended to do,
  and why was it done this way?" · <https://doi.org/10.1145/1937117.1937125>; figures and quotation
  verified 2026-09-13 against the workshop's PDF,
  <https://ecs.victoria.ac.nz/twiki/pub/Events/PLATEAU/2010Program/plateau10-latoza.pdf>
  (LaToza's 2012 dissertation reanalyses the same survey as 374 questions, 92 distinct, in 18
  categories).
- **Roehm, Tiarks, Koschke and Maalej (ICSE 2012).** Observation of 28 professional developers in
  seven companies: developers "put themselves in the role of end users by inspecting user
  interfaces", "try to avoid program comprehension", treat it "as a subtask of other maintenance
  tasks", prefer "face-to-face communication … to documentation", and "we did not observe any use
  of state of the art comprehension tools and developers seem to be unaware of them" ·
  <https://doi.org/10.1109/icse.2012.6227188>.
- **Wettel, Lanza and Robbes, CodeCity (ICSE 2011).** A controlled experiment "in four locations
  across three countries, involving 41 participants from both academia and industry" on a 3D
  city-metaphor visualisation: "a statistically significant increase in terms of task correctness
  and decrease in task completion time"; the authors' project page gives the sizes: "24% more
  correct and obtained in 12% less time than when using Eclipse or spreadsheets with metric data"
  — verified 2026-09-13 against the paper body (author copy
  <https://wettel.github.io/download/Wettel11a-icse.pdf>): "CodeCity enabled an increase in
  correctness of 24.26% over Ecl+Exl" and "a completion time reduction of 12.01% over Ecl+Exl",
  both "statistically significant"
  · <https://doi.org/10.1145/1985793.1985868>, data at <https://doi.org/10.5281/zenodo.268463>,
  <https://wettel.github.io/codecity-experiment.html>. The tasks were reverse-engineering and
  metric questions, not modification tasks. A 2022 replication in VR (24 and 26 participants) found
  VR "performed the assigned tasks in much less time, while maintaining a comparable level of
  correctness" · <https://doi.org/10.1016/j.infsof.2022.107064>.
- **Nam et al. (ICSE 2024).** 32 participants; the prompt-less in-IDE explain plugin "can aid task
  completion more than web search"; "usage and benefits differ between students and
  professionals". Task completion, not retained understanding, was the measure ·
  <https://doi.org/10.1145/3597503.3639187>.
- **Generated wikis and tours.** CodeWikiBench scores documentation with "LLM-based assessment
  protocols" (<https://doi.org/10.18653/v1/2026.findings-acl.288>); SWD-Bench (arXiv, 2026-04-08)
  evaluates repository documentation "by assessing an LLM's ability to understand and implement
  functionalities using the documentation" (OpenAlex record; corrected 2026-09-13: the preprint
  is <https://arxiv.org/abs/2604.06793>). Neither measures a human reader. The code-tours plan
  lists automatic evaluation as an open challenge (<https://doi.org/10.1145/3696630.3731462>);
  the same group's 2026 study with 26 developers then found LLM evaluation of tours
  "unreliable: sycophancy, confabulation, and incoherence were pervasive"
  (<https://arxiv.org/abs/2607.26987>; added 2026-09-13 from the
  [literature addendum](literature-addendum.md#corrections-proposed)). Google's generative-UI evaluation is rater
  preference, not learning. Litt offers personal anecdote and says so
  ([talk note, evidence](understanding-bottleneck-talk.md#evidence-and-anecdotes)).
- **What this says about the situation model.** In Pennington's terms (Phase A), the evaluated
  aids act on the program layer: navigation cost (Ko, Lawrance), structural questions (Wettel),
  and task completion with a selection explained (Nam). No study found measures whether exploring
  a map or a micro-world builds the situation model or the rationale layer, which LaToza and
  Myers identify as the hardest questions; Roehm's field observation is that professionals under
  pressure avoid comprehension and did not use research tools at all. The evidence note's
  summary of what reading and approving transfers applies unchanged
  ([evidence note, summary table](evidence-and-mechanisms.md#summary-table)).

## Open questions in the sources

- Storey et al. (2000): whether a tool can "enhance or ease the programmer's preferred strategies"
  rather than impose one is stated as the design question, not answered
  (<https://doi.org/10.1016/s0167-6423(99)00036-2>).
- LaToza and Myers (2010): intent and rationale questions are the most frequent hard ones; the
  paper frames "opportunities … for developing new languages and tools that make answering these
  questions easier" as open (<https://doi.org/10.1145/1937117.1937125>).
- Roehm et al. (2012): "a gap between program comprehension research and practice"; "Our findings
  call for … reconsidering research agendas" (<https://doi.org/10.1109/icse.2012.6227188>).
- Litt (2026): interactivity "can just be a crutch, and it can be kind of slop"; whether a
  micro-world gives "peripheral vision" is asserted from experience
  ([talk note](understanding-bottleneck-talk.md#proposal-3-micro-worlds)).
- Google Research (2025): generation takes "a minute or more" and outputs are sometimes inaccurate,
  "areas of ongoing research"
  (<https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/>).
- Codemaps and DeepWiki docs: neither says whether a map or wiki persists a human's notes across
  regeneration; DeepWiki's answer is to move the human's input upstream into `wiki.json`
  (<https://docs.devin.ai/desktop/codemaps>, <https://docs.devin.ai/work-with-devin/deepwiki>).
- Eraserbot: whether hand edits to a generated diagram survive the next monitored-file update is
  not stated (<https://docs.eraser.io/docs/eraserbot>).
- CodeWiki (2026): evaluation is LLM-judged; human comprehension is not measured
  (<https://doi.org/10.18653/v1/2026.findings-acl.288>).
- Karpathy (2026): keeping a compounding wiki honest needs "lint" passes for "stale claims" and
  "contradictions"; the gist leaves the implementation open
  (<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>).
- Code-tours plan (2025): "automatically evaluating the quality of generated tours" is listed as
  unsolved (<https://doi.org/10.1145/3696630.3731462>).
- Glamorous Toolkit: "Do I need this environment in the AI age? More than ever" is an assertion on
  a product page with no study behind it (<https://gtoolkit.com/>).

## Dead ends

- **Web search unavailable.** The session's WebSearch budget was exhausted before this pass;
  DuckDuckGo's HTML endpoint returned an anomaly page, and the arXiv API returned HTTP 429. Paper
  discovery used OpenAlex and Semantic Scholar; tool discovery used the GitHub API and known URLs.
  Consequences: "codebase visualisation with LLM" papers were sampled, not swept; Obsidian- or
  Foam-style code vaults were not found (Foam is a general PKM extension,
  <https://github.com/foambubble/foam>, and no code-vault primary source was located); Replit was
  not fetched; IcePanel's drift-detection was not confirmed beyond its home page.
- **Mutable.ai.** `blog.mutable.ai` does not resolve; the acquisition and shutdown rest on
  PitchBook and a Hacker News comment.
- **CodeSee.** `codesee.io` returns 404; the Phase A entry is the last description.
- **Sourcetrail's discontinuation post** is only on the Wayback Machine, which this environment
  cannot fetch; the archive notice in the README is the primary record.
- **Sourcegraph Notebooks** are absent from the current docs (`/docs/notebooks` 404); their
  retirement was not confirmed from a Sourcegraph statement.
- **Google Code Wiki's application page** renders no content without JavaScript; per-page chat and
  editing could not be checked.
- **Understand's Annotations help article** is JavaScript-only; the 2021 vendor blog post was used
  instead.
- **Anthropic "Imagine with Claude"**: 404 at `anthropic.com/news/imagine-with-claude` and
  `claude.com/blog/imagine-with-claude`.
- **Observable** documentation: HTTP 429 on every fetch.
- **Multiplayer.app** no longer describes runtime-generated architecture diagrams on its home page.
- **Wettel's percentages** came from the author's project page; resolved 2026-09-13 — the ICSE
  paper body (author copy on wettel.github.io) gives 24.26% and 12.01%, as recorded above.
- **SWD-Bench's arXiv identifier** was not retrieved (OpenAlex record without DOI)
  (corrected 2026-09-13: <https://arxiv.org/abs/2604.06793>).
- **No evaluation with humans** of DeepWiki, Code Wiki, Codemaps, Swimm Explore, Understand
  Anything, GitDiagram, or CodeBoarding was found; no study of an agent-generated debugging UI
  was found. (corrected 2026-09-13: the original sentence also claimed no human evaluation of
  any AI-generated tour; Balfroid et al. (<https://arxiv.org/abs/2607.26987>, 26 developers,
  qualitative) and LACY (<https://arxiv.org/abs/2603.25391>, FSE 2026 Industry, five learners,
  quiz 83% versus 57%) evaluate LLM-generated code tours with humans — see the
  [literature addendum](literature-addendum.md#corrections-proposed).)
- **The directory-tree-with-persistent-annotations idea** has no single implementation; see the
  closing paragraph of [Directed questions on a node](#directed-questions-on-a-node).
